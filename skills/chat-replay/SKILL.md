# chat-replay · 聊天记录回放

五个动作，一条时间线：

| 动作 | 画面 | 用在什么时候 |
|---|---|---|
| **弹出** | 气泡从头像一侧带一点回弹地冒出来 | 每一句对白——说到哪句，哪句出现 |
| **正在输入** | 对方头像旁先冒一个跳动三点的气泡，到点换成正文 | 制造「等回复」的悬念；对方犹豫、迟疑、憋大招 |
| **我方输入** | 输入框里逐字打出，按下发送键，输入框清空、气泡弹出 | 「我」这一方斟酌措辞；口播里「我当时打了一句……」 |
| **上推** | 消息排满视口后整列上推，最新一条始终完整可见 | 对话变长时自然发生，不用管 |
| **强调** | 其余气泡变暗，目标气泡描边，荧光笔划过关键词；可推近 | 「看这句」——口播落到那句话上的那一刻 |

## 分工：你决定内容与节奏，脚本只做机械活

**你（agent）负责**：对话文本（逐字、脱敏）、谁在左谁在右、每句在口播的哪一秒出现、谁「正在输入」多久、强调哪句哪几个字、用哪种画框与底。
**脚本负责**：断行与气泡几何、滚动量、头像与图片重编码进预算、各动作的入场与驻留、gsap-emit 发射，以及自检。

这是**技法**不是模板：脚本里没有示例对白、没有栏目色板、没有某个 App 的界面。同一份脚本给不同口播产的颗粒应当长得不一样——差别在你写的 spec。

## 先想清楚：该用它吗

- **要「原样为证」**（真截图、要观众相信这就是原记录）→ 用 `doc-reveal` 展示**原截图**（叠放 + 局部强调）。
  本技法是**重排版回放**：画面是重新画的，不是证据。
- **要「把一段对话讲出来」**（节奏、悬念、哪句是重点）→ 用本技法。
- 对话是**转写或情景还原**时，MUST 在 `frame.stamp` 标「示意」「情景还原」「已脱敏」之类的字样；
  MUST NOT 用它伪造真实人物的聊天记录、冒充真实证据。

## 工作流

### 1. 整理对话

- **逐字**誊写要上屏的句子；长句拆成几条（一条气泡超过视口高脚本会拒绝）。
- **脱敏**：真名、手机号、头像换掉；群名改成概括性的称呼。头像不给图就用名字首字 + 中性底色。
- **去 emoji**：渲染服务端字体表没有彩色 emoji，会出豆腐块——脚本会拦。改成文字（「（笑）」）或做成图片消息。
- 开场就该在屏上的历史消息（不需要逐条弹出的上文）放在 `messages` 最前面、**不给 `t`**。

### 2. 按口播定节奏（最要紧的一步）

拿句级时码（`transcript.json` 的 `st/ed`）按字数内插估某句的时刻，减去颗粒起点 `track_st` 得到颗粒内时刻。经验值：

- 每条气泡的 `t` = 口播**开始念**这句对白的时刻（或念到它的前一拍）。
- **读时**：相邻两条之间至少留 `0.18 s × 上一条字数`，最少 1.2 s；连发的短句（「好」「成交」）可以 0.6 s 一条。
- `typing`（对方正在输入）0.6–1.6 s。只给真有「等」的那几句，每句都加会拖沓。
- `compose`（我方在输入框里打字）≈ 0.07 s × 字数，0.8–2.2 s 之间。超出输入框宽的长句会自动左推。
- 一个 beat 里 `focus` **不超过 2 处**，每处停留 ≥ 2 s。`t` 压在口播说到那句话的时刻，`mark` 写那句里**真正的重点词**（逐字匹配原文）。
- 最后一条消息之后至少留 0.5 s（脚本会拦）；强调之后不再大动，画框轻浮驻留到坑位末尾（铁律 7）。

### 3. 写 spec

字段全表见 `references/spec.md`。要点：

- `id` = 派单的 `composition_id`；`duration` ≥ 坑位包络 `track_ed − track_st` + 0.3。
- 画框 `frame.kind`：`phone`（竖长手机，缺省）/ `panel`（宽的桌面窗口）/ `none`（只有气泡，叠在底轨上用，配 `bg: transparent`）。
- 底 `bg`：`light` / `dark` / `transparent` / `#RRGGBB`。**栏目有自己的色就用 `palette` 注入**（我方气泡、强调色、荧光笔色……），别改脚本预设。
- `stack`：`top`（缺省，像真实 App 从顶往下排）/ `bottom`（最新一条始终贴视口底，每来一条整列上推，视线固定在一处）。
- 文案卡放画框另一侧（缺省左栏 x 96 起），内容底沿 ≤ 0.85 H（字幕带）；**推近时**画框会变大，脚本会算推近后的画框是否钻到卡底下，钻了就报出 `anchor[0]` 的下限。
- spec 落在产物旁边（如 `<工程>/mg/<composition_id>.spec.json`），日后改节奏只改 spec 重生成。

### 4. 生成 → lint → 验收

```bash
python scripts/chat_replay.py <spec.json> --out <工程>/mg/<composition_id>.html
gtrk mg lint <工程>/mg/<composition_id>.html --dispatch <工程>/split/dispatch.json
python scripts/chat_check.py <工程>/mg/<composition_id>.html --out <系统temp>/sheet.png [--video <系统temp>/preview.mp4]
```

- 产物**直接写最终落点**，不经中转目录。生成器 stdout 的 `chars` 必须 < 1,900,000（纯文字对话通常 1–3 万字符；图片消息每张约 3–8 万）。
- lint 的 `x-soft-alpha` 是信息项（气泡投影、变暗、荧光笔都是半透明），不用改。
- `chat_check.py` 的读数怎么看见下文「验收」。`--video` 逐帧 seek 出一段本地预览 mp4，只给人看节奏，不是验收。
- **预检不是验收**：本地 chromium 用本机字体，真验收 = 真渲染引擎抽帧（`gtrk mg render` / `gtrk render`）。

### 5. 交回铺轨

铺轨不在本 skill 内——派单模式交回 `/gtrk-mg`（`gtrk mg --project`），独立模式走 `gtrk mg render <html> --duration <s>` 出透明 MOV。

## 排版为什么不交给浏览器

每行文字在生成期就断好（`white-space:pre`），每条消息绝对定位。这样**气泡高度、滚动量、推近目标在生成期就是确定数**：
同 spec 逐帧一致，滚动不会因为渲染端字体略宽而多出一行、把最新一条推出视口。

代价是断行用的是**估算字宽**：内置一张思源黑体 CN Medium 的 ASCII 步进宽度表（取自字体文件的字形度量；思源黑体以 SIL OFL 1.1 发布），
CJK 与全角标点按 1 em，再整体放大 4% 作安全余量。估得准不准由 `chat_check.py` 在浏览器里量出来（`est_ratio`）。
换了字体（`fonts.sans`）时字宽会变，MUST 重跑 `chat_check.py` 看 `bubble_w_over`。

断行规则：拉丁单词与网址不拆（超长才逐字拆）；句读、右括号不落行首，左括号不落行尾；段末只剩一个字时从上一行挪一个字下来。

## 自检（脚本当场退出、不产文件）

| 查什么 | 为什么 |
|---|---|
| 文本里有 emoji | 渲染端字体表没有彩色 emoji，出片是豆腐块 |
| 相邻两条的 `typing` / `compose` 窗口挤在一起（< 0.2 s） | 上一条还没落定，下一条的「正在输入」就冒出来，观众分不清谁在说 |
| 第一条消息早于画框入场落定 | 画框还在飞，气泡已经在弹 |
| 最后一条离颗粒末尾不到 0.5 s | 没有驻留，最后一句一闪而过 |
| 不带 `t` 的开场消息排在带 `t` 的后面 | 开场已在屏上的消息只能是上文 |
| 一条气泡比视口还高 | 一屏放不下，滚动也救不了——拆成几条 |
| `focus` 早于目标消息出现 / `mark` 在原文里找不到 | 还没出现的消息没法强调；改了文案忘了改 mark |
| 推近后目标气泡出画、落进字幕带，或画框钻到文案卡底下 | 推近的意义就是看清那句，被卡挡住等于白推（报出 `anchor` 下限） |
| 消息视口底沿落进字幕带 | 最新一条消息正好在字幕位置，被压住 |
| 文案卡压到画框、或底沿进字幕带 | 同上 |
| `palette` 里有不认识的键 | 拼错键名会静默不生效 |
| 产物超字符预算 | 客户端静默拒挂 |

## 验收：`chat_check.py` 的读数

| 读数 | 合格线 | 量的是什么 |
|---|---|---|
| `messages[].vis` | ≥ 0.995 | 每条消息出现 0.6 s 后，气泡落在视口内的面积比（1 = 完整可见） |
| `typing[].vis` | ≥ 0.995 | 每个「正在输入」气泡出现 0.35 s 后的可见比 |
| `bubble_w_over` | ≤ 1 px | 气泡实际宽 − 生成期上限；> 0 即断行估窄了，字撑破了气泡上限 |
| `bubble_h_err` | ≤ 1 px | 气泡实际高 − 排版高；≠ 0 即上下两条会叠 |
| `est_ratio` | 信息项 | 每行真实字宽 / 估宽。纯中文 ≈ 0.96（就是那 4% 余量）；拉丁偏多时 ≈ 0.87（估宽偏保守） |
| `frames` | 相邻不同 | 抽样帧 sha1，相同 = 冻结 |

任一不合格退出码 1。

## 这个技法**不做**什么

- **不仿任何具体 App**：不用某个 App 的标志色、图标、气泡尾巴形状、状态栏。画框是中性的圆角机身 / 窗口。
- **不做 App 特有元素**：语音条、红包、转账、撤回动画、已读回执——这些是某个 App 的签名，也最容易被误认成真截图。
- **不配音**：产物无声，消息提示音在 NLE 里叠。

## 硬约束（不满足别交付）

1. gsap-emit v1 全部铁律——脚本已按此发射，别手改产物 HTML 去违反它。
2. 零卷积：只用 `box-shadow` 与渐变，不加 `filter: blur()` / `drop-shadow()`。
3. 字体名命中渲染服务端字体表；缺省思源栈已命中，换字体要自己核，并重跑 `chat_check.py`。
4. 画幅 = 目标工程画幅；竖屏工程另写一份 spec（`width/height` 与 `frame` 几何按新画幅给）。
5. 对话是转写或还原时 MUST 标 `frame.stamp`；MUST NOT 伪造真实人物的聊天记录。
